**Measured on 2026-10-05 (facts, not inference):**

  - **The fix is in the running binary.** lldb resolved the live process to `.build/out/Products/Debug/Me`, which is byte-identical in size and mtime (10-04 16:11) to `.build/debug/Me`, while `ContentView.swift` is 10-04 00:32 — `find Sources -newer <binary>` returns nothing.   - **The window was 1483×1342 at (22,45)**, from `CGWindowListCopyWindowInfo` run in a separate process (plus a 500×500 window at (0,940)). That is ~283pt wider than the 1200pt `defaultSize`, which is the one fact that differs from the 2026-10-04 verification.
  - The process had 12 threads, 0% CPU, and its main thread fully idle in `ReceiveNextEventCommon` per `Me_hang_2026-10-05-084113.spin` (229 KB) — i.e. responsive, not wedged. It then exited on its own; no `Me_*.ips` crash report exists.

**Cause, ranked.** All three are defects of the *fix*, which is why this can regress with the source unchanged — see `ContentView.swift:640` (`MainWindowChrome`, attached at `:292`).

  1. **The fix was never durable.** `alignTitlebarBackground()` (`:686-692`) writes `titlebarBackground.frame.origin.x` — a frame AppKit owns and recomputes on the next layout pass. Only three notifications put it back (`NSSplitView.didResizeSubviews`, `NSWindow.didResize`, `NSWindow.didBecomeKey`), so any other layout pass discards the value silently. Yesterday's "confirmed fixed" caught it in the window where our value still held. Corroborating detail: `titlebarSeparatorStyle = .none` *is* durable (a window property), so only the seam coming back — with no other visual change — is exactly what this predicts.
  2. **The target is guessed by shape, not identity, and the window is wider than when it was verified.** `:668` takes the *first* `NSTitlebarBackgroundView` with `origin.x > 0`; `:681-684` takes the **widest** `_NSSplitViewItemViewWrapper` with `origin.x > 0`. At 1483pt there may be a third wrapper, and the widest one may not be the detail column — which would place the seam at a different x rather than remove it. **This is the hypothesis that explains "fine yesterday, back today" with identical code, and the only one still testable.**
  3. **`updateNSView` (`:712`) is not the safety net it looks like.** `.background(MainWindowChrome())` supplies no inputs, so SwiftUI may call it once and never again — it is not a per-ContentView-update re-align.

**Two wrong turns from this session, recorded because both would have produced a confident wrong answer:**

  - `expr -l swift` in lldb evaluates on lldb's expression thread, **off the main thread**, where AppKit returns an empty array — `NSApplication.shared.windows.count` read **0** while `CGWindowList` showed 7 on-screen window records for the same pid. Any view-tree probe must pass **`-T 1`**. This is `AGENTS.md`'s "suspect the measurement first" in its purest form: a plausible number, not an error.
  - I first assumed every ContentView state change re-aligned the titlebar, via `updateNSView`. Wrong for the reason in 3.

**Method notes for whoever finishes this.** `screencapture` still fails ("could not create image from display"); `CGWindowListCopyWindowInfo` run from a *separate* Swift script is the one window-level API that works and needs no permission (owner PID, bounds, layer — window *names* come back nil). In lldb, prefer `expr -l swift -T 1` with `print`; the ObjC++ path fails on any variadic selector (`appendFormat:`, `printf`), and `object_getClassName` needs `(char *)`/`(const char *)` casts. **Never** mutate a subview frame from an `NSWindow.didUpdateNotification` observer — it re-triggers the update and hung the main thread (watchdog spin files). Use `view is NSSplitView` / `.contains(...)`, never `== "NSSplitView"`, because `object_getClassName` returns `NSKVONotifying_*` subclasses.

**Suggested fix (not written yet), aimed at making a third recurrence impossible rather than rarer.** Stop poking on selected notifications and instead observe the titlebar background view's **own frame** (KVO on `frame`), re-aligning whenever AppKit moves it; the existing `> 0.5` guard makes that converge in one extra pass. Add a DEBUG log naming class, old x, new x and the trigger, so any future recurrence is explained in the log instead of re-derived. Optionally assert the alignment in DEBUG builds so it fails in development rather than on a screenshot.

**Standing caveat.** This is the project's first fix that lives entirely in the *view* layer, so it has no test and no tripwire — `scripts/quality-check.sh` cannot see a pixel. Per `QUALITY_RISKS.md`'s closing note ("this register cannot see defects that have no metric"), it is unmonitored by construction.

## HIGH: 274 unchecked `try? context.save()` sites (found 2026-09-26, **closed 2026-09-27**)

- [x] **Audit `try? (context|modelContext).save()` — 274 occurrences across 71 files, zero of which inspected the result.** Closed 2026-09-27: all 274 converted to `Commit.save(_:_:)` (`Sources/MeCore/Store/Commit.swift`), a lock-guarded helper that logs the failure via `Logger(subsystem: "com.me.app", category: "store")` and returns a discardable Bool. The label is the enclosing func name in MeCore (`ensureMapFlags`) and `Type.func` in views (`EventDetailView.save`) so a log line names something actionable. Control flow is unchanged — a failed save still continues to the next step rather than aborting.
- [x] **Make the launch chain report failures instead of swallowing them.** `SeedRunner.start`'s completion was `() -> Void`, structurally incapable of reporting. It now carries `[String]` of failed operations, collected by `Commit.collectFailures { }` around the whole chain (a lock-guarded collector stack, so nested scopes unwind cleanly and view-layer saves outside the scope are logged only). `SplashScreenView` hands the result to `StartupReport.shared`, and `ContentView` renders a dismissible top banner naming the affected operations. This was the actual fix for the serious failure mode: a failed save leaves the change pending in the context, so a persistently-bad row poisons *every* later save in the chain, and the old final `try? context.save()` hid the aggregate result.
- [x] **Add a build-time guard.** `MeCoreTests.testNoUncheckedTrySaveInSources` (`Tests/MeCoreTests/MeCoreTests+StoreHygiene.swift`) walks `Sources/**/*.swift` and fails on any `try?` save, reporting `file:line: source`. Verified to fail on an injected violation, including the no-space `try?modelContext.save()` form. It also `XCTSkip`s (rather than silently passing) if it cannot locate the repo root, so a moved checkout cannot quietly disable it.
- [x] **Do not touch the 409 `try? …fetch` sites** — `?? []` degradation there is idiomatic and safe, and the lint deliberately does not match them.
